# Rollout хранения refresh-токенов

Refresh-токен хранится в Redis только как SHA-256 digest, а значение привязано
к текущему `users.token_version`. Создание token key, добавление digest в
пользовательский индекс и TTL индекса выполняются одним Lua-script. Consume,
точечный revoke и `revoke_all` также атомарны относительно новых login/refresh
операций.

## Legacy-сессии

Старые Redis-записи содержат raw refresh token и только user id. Они не могут
доказать актуальный `token_version`, поэтому после обновления не принимаются.
При первой попытке refresh legacy-запись атомарно удаляется вместе с её
индексом, API возвращает штатный `401 Invalid or expired refresh token`, и
клиент должен выполнить обычный вход заново.

Это намеренная одноразовая инвалидация: после истечения короткого access token
все активные до rollout web-сессии могут попросить повторный вход. Она должна
быть объявлена перед релизом и выполняться в согласованное окно. Откат старого
runtime после появления digest-записей небезопасен: старый код не понимает
versioned value. При rollback сначала завершить новые web instances, очистить
refresh/user-token keys и только затем запускать старую версию; пользователи
после такого rollback также войдут повторно.
